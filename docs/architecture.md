# Architecture

## Source layout

| Path | What it is |
|------|------------|
| `src/azzurra.c` | The cartridge: app states, renderer, HUD, menus, events → effects. Entry points `azzurra_init`, `azzurra_update`, `azzurra_draw`. |
| `src/az_core.h` | The rules: ball flight, net, bounces, line calls, doubles scoring and serving, human and computer players. No PRG32 call; integer arithmetic only. |
| `src/az_net.h` | Online play: the lobby and lockstep snapshots packed into the server's five fields, and the lockstep input ring. No PRG32 call. |
| `src/az_music.h` | Pattern/order sequencer and a three-slot stereo effects player. Calls PRG32 only through the `AZ_NOTE_ON`/`AZ_NOTE_OFF` macros that the includer defines. |
| `src/gen/art.inc` | Generated by `tools/build_art.py`: geometry, palettes, skylines, courts, sprites, font, names. |
| `src/gen/music.inc` | Generated by `tools/build_audio.py`: patterns, songs, effects. |
| `audio/audio.json` | Generated by `tools/build_audio.py`: the 21 SID-like instruments, which PRG32's `tools/prg32audio_pack.py` packs into the cartridge's AUD0 block. |
| `metadata/*.json` | Store metadata and colophon: the single source of truth for name, version and credits. |
| `assets/store/` | `icon.png`, `screenshot.png` (the splash) and `preview.mp4` for the Store. |
| `assets/png/` | Contact sheets of the generated art (for review only; not used by the build). |
| `tools/` | Art and music generators, palette solver, relocation and bundle checks. |
| `scripts/` | Build, QEMU capture and preview, Store bundle packing. |
| `tests/` | Host tests: `test_core.c` (the rules and the lockstep), `test_game.c` (the whole cartridge on a fake PRG32), `test_net.c` (two to four cartridges on a simulated server), `run_tests.sh`. |

The cartridge is a single translation unit: `azzurra.c` includes the
generated data and the two headers. The cartridge is built with these
constraints:

* **Compiler:** `riscv32-esp-elf-gcc`, `-nostdlib`, for RV32IMAC.
* **No floats and no 64-bit division.** The host tests compile the same code
  with `-Wall -Wextra -Werror` and AddressSanitizer/UBSan.
* **No pointer in initialised static data.** Portable cartridges have no
  relocations; `tools/check_relocatable.py` proves it for every build.
* **`memset`/`memcpy` are defined locally**, because the compiler may emit
  calls to them for structure copies.

## Timing

`azzurra_update` runs the game in fixed 33 ms ticks (`AZ_TICK_MS`) measured
with `prg32_ticks_ms()`, and catches up at most 3 ticks per call
(`MAX_CATCH_UP`). The game therefore keeps the same speed when drawing is
slower, as on the ESP32-C6's SPI panel. Physics, AI, the music sequencer and
the effects all advance on these ticks. `azzurra_draw` renders the current
state once per call.

## App states

```
TITLE ──A──▶ INTRO ──3.3 s / A──▶ PLAY ──match over──▶ ROUNDWON ──A──▶ INTRO (next city)
  │  ▲                               │  ▲                 │
  │  └────────────── B ────── PAUSE ◀┘  └ START           └─ round 14 ─▶ CHAMPION ──A──▶ TITLE
  │                                                     GAMEOVER ──A──▶ INTRO (same city)
  ├─15 s idle──▶ DEMO ──any key──▶ TITLE                    └──B──▶ TITLE
  └─PLAY ONLINE──▶ LOBBY ──all ready, 3 s──▶ INTRO ▶ PLAY (online) ──▶ result ──A──▶ LOBBY
                    │  └──no server──▶ NETMSG ──A──▶ TITLE    └─ a console lost ─▶ NETMSG ──A──▶ LOBBY
                    └─LEAVE / B──▶ TITLE
```

Music plays only in TITLE (and the LOBBY, which is part of the title),
ROUNDWON, GAMEOVER and CHAMPION. INTRO, PLAY, PAUSE and DEMO play effects
only. `tests/test_game.c` checks that no music
plays during PLAY.

## Online play

The PRG32 multiplayer API relays, for each console, five fields about every
50 ms: `x` and `y` (16 bits each), `sprite` and `flags` (16 bits each) and
`input` (7 bits), 71 bits in all. `src/az_net.h` uses them in two ways.

**In the lobby** (`flags` phase 1) a console publishes its team, READY and,
for the host, the match, the city, the games, the seed, the slot map (four
4-bit places; 15 is a computer player), the number of consoles, a hash of
their player IDs and a 4-bit match tag. Clients start when they see the
host's start with their own roster hash.

**In a match** (`flags` phase 2) the game runs in **lockstep**:

* Every console records its input for tick *t* + 5 (`NET_D`) and publishes
  its inputs for the last 11 ticks (`NET_W`): one of 36 symbols per tick
  (LEFT/none/RIGHT × UP/none/DOWN × A × B), packed three symbols to 16 bits.
* A console advances tick *t* only when it holds every console's input for
  *t*. It records its own input only after that check, so no console is ever
  more than 2 × 5 + 1 ticks ahead of the slowest one. The window of 11 ticks
  therefore always covers what a peer is missing, even when a snapshot is
  lost.
* The tick is sent modulo 64 and widened to the nearest value on receipt.
* The rules (`az_core.h`) take the four players' inputs and are integer-only
  and deterministic, so the same seed and inputs give the same match on
  every console. `tests/test_net.c` compares a hash of the whole game state
  on every console at every tick.

A console that is behind catches up at up to 3 ticks per update, like a
local match. A console that is not heard from for 2.5 s (`LOST_MS`), or
that leaves the room, ends the match on all the others.

**The far end.** A console on the far team draws the world turned through
180°: x and y are negated before projection, the near and far sprite views
are swapped, the court rows are mirrored, and the skyline is the city's back
view (scene `city × 2 + 1`). Its human player has `rot` set, so `az_human`
turns the D-pad. Drawing never changes the game state, so both views come
from the same match.

## Renderer

The screen is 320 × 200 in three bands:

| Rows | Band | Source |
|------|------|--------|
| 0–9 | Score bar (HUD) | Filled by code. Text: Azzurra's games and points, the city, the rivals' points and games. |
| 10–49 | City skyline | `view_data`: one 40-row run-length picture per city, 6-bit local colours mapped through `view_map`. |
| 50–199 | Stadium and court | `court_data`: one 150-row run-length picture per surface (stands, crowd, wind screen with sponsor boards, umpire's chair, court and lines in perspective). |

The camera is a pinhole projection (`tools/geometry.py`, constants `G_F`,
`G_H`, `G_CAM_D`, `G_HZ` in `art.inc`). The far baseline is at y=98, the net
at y≈129 and the near baseline at y=182. `az_sx`, `az_sy` and `az_px` in
`az_core.h` are the same projection in integers, so the sprites stand exactly
on the court that the Python tools painted.

Every frame, `render()` does three things:

1. **Collects sprites:**
   * the net (a see-through mesh drawn as a sprite, so that depth sorting
     works around it);
   * the sponsor boards;
   * the four players, scaled by depth from 34 × 58 (back view) and 22 × 36
     (front view) frames;
   * the ball and its shadow;
   * on the champions' screen, the trophy and confetti.
2. **Compares the sprite list with the previous frame's.** For every sprite
   that moved or changed, it marks the rows (and the x span) that it covered
   before and covers now as dirty. Text changes mark their rows too.
3. **Rebuilds and sends every dirty row.** For each one, it:
   1. decodes the background row into a 320-byte line buffer;
   2. blends in every sprite that crosses the row, far to near;
   3. draws the text layer on top;
   4. sends only the dirty span, in one of two ways:
      * as runs of `prg32_gfx_rect_indexed` (one call per colour run);
      * as an 8-bit indexed row sprite (`prg32_sprite_draw_indexed`), when
        the span has more than 72 runs (`MAX_ROW_RUNS`).

The frame is presented in two boxes, rows above and below y=118
(`SPLIT_Y`), each only if one of its rows changed.

No full picture is ever kept in cartridge RAM, and nothing is ever erased: a
sprite's old pixels disappear because their rows are rebuilt from the
background.

`tests/test_game.c` checks this invariant on every screen: the panel after an
incremental frame must equal a clean repaint of the same state.

## Memory and size budget (128 KiB profile)

These are the figures from the build log of version 2.1.0
(`build/azzurra-pro-tennis-*.build.log`), measured:

| Item | Bytes |
|------|------:|
| Code + read-only data (`code=`) | 116,844 |
| Cartridge memory image incl. BSS (`mem=`) | 123,492 of 131,072 |
| AUD0 audio block | 208 |
| Package, ESP32-C6 (with Store trailer) | 127,782 of 131,072 |
| Package, QEMU | 127,780 of 131,072 |

2.0.0 had `code=` 80,864. Of the 35,980 bytes added in 2.1.0, the back
views take 26,930 (their pictures, row offsets, palettes and colour maps); singles, the
lobby and the lockstep take the rest. 3,290 bytes of the package limit are
left (ESP32-C6 package).

The largest items of read-only data are:

| Data | Bytes |
|------|------:|
| City skylines, front and back | 46,531 |
| Court pictures | 15,490 |
| Sprites | 7,600 |
| City palettes, 28 views | 5,488 |
| Music patterns, songs and effects | 3,078 |

The game state (`az_game_t`, four players, the ball, events) is a few hundred
bytes. The renderer's line buffer, sprite lists, dirty-row table and text
layer (25 × 40 characters) take about 4 KiB.
